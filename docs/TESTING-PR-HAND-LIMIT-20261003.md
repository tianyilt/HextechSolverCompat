# 手牌上限 PR：原生复现、固定搜索对照与未通过项

当前源码候选修复了手牌上限变化未参与续算判断的问题；两项关键原生检查通过。固定搜索对照的动作、工作量、预测战损和真实执行结果一致，**耗时无明显增加的验收尚未通过**。本稿保留失败和全部样本，不用于宣称提速、无性能退化或可按完整验收合并；当前公开提案以Draft提交。

## 问题与实现

根快照是搜索开始时冻结的战斗状态，分支复制后继续拥有其冻结值。状态指纹用于区分搜索状态；续算标识用于判断实战是否仍符合已算路线。BaseLib 的真实可选接口 `IMaxHandSizeModifier` 可以改变手牌上限，RitsuLib 会查询最终上限，求解器已经在根中保存该值。

修改前，将上限设为 13，捕获根和兄弟分支，再将实战上限改为 16：旧根和兄弟仍为 13，新根为 16，但实战续算文本没有改变。该失败在官方 0.48.1 上实际复现；同项适配器修复在专用实验中已关闭。

候选在实战续算标识中追加原生最终值，在预测标识中追加分支冻结值，在搜索指纹中追加玩家身份及冻结值。玩家列表顺序在根捕获时冻结，分支继承同一顺序，使用索引遍历，不在每次计算指纹时重新排序。不增加 BaseLib 硬依赖，也不放宽未知效果或补丁拒绝。

当前候选实际通过 Dredge 上限 13、CrashLanding 上限 5：原生与预测完整状态一致；13→16 的实战变化使旧续算失效，旧根/兄弟/预测标识保持稳定；恢复 13 后实战标识恢复。严格回读收据为 [pr0481-indexed-native-verification.json](../evidence/pr/pr0481-indexed-native-verification.json)。官方原版与同条件源码基线的相关 1,170 个方法规范化 IL 全部一致，原版失败不能归因于基线编译改变了这一机制。

## 固定搜索输入与测量方法

铁甲战士，种子 `HEXTECHCOMPAT`，遭遇 `FUZZY_WURM_CRAWLER_WEAK`，敌方当前生命 48、初始行动 `INHALE`，玩家初始生命 80。清空牌堆后，手牌放 3 张打击和 3 张防御，抽牌堆放 6 张打击和 6 张防御；持有 `OVERFLOW_RUNE`。三个用例名 `warmup`、`sample-1`、`sample-2` 使用完全相同的语义 JSON。

请求固定搜索预算 5,000ms、节点上限 3,000、配置 Beam 40、最大并行度 1；关闭增量回放诊断、详细诊断和 No-GC（暂停垃圾回收的特殊模式）。**实际运行的主组合成员宽度为 27**，其余组合成员以 `AcceptableBattleHpLoss` 跳过；配置值不冒充实际执行值。每个实际成员和跳过原因都保存在收据的 `portfolioMembers` 中。这里测量 `solverMetrics.totalElapsedMilliseconds`，不使用建局、动画、等待 ready 或请求总墙钟时间作为搜索耗时。

顺序为修复版第一进程、原版第一进程、原版第二进程、修复版第二进程。每个进程先做一次预热，再测两次，总计原版与修复版各 4 个计时样本。两版不同时运行，兼容版主矩阵在测量期间暂停。**每个请求前清除专用 PR 副本的路线缓存 JSON**，确保实际重新搜索；不改变生产搜索代码。缓存开启时的初次试验被明确排除，不能计作独立耗时样本。

## 保留的失败与方法修正

1. 首次非平凡场景使用零时间预算，原生在 `BeamWidthPortfolioGate.RejectRefinement` 因 `timeBudgetMilliseconds=0` 抛出参数异常。将两版共同输入改为正的 5,000ms；没有扩大请求超时或删效果断言。见 `pr-sentinel-initial-failure.json`。
2. 后续三次相同搜索指标来自已保存路线的复用，排除这些计时，见 `pr-sentinel-cache-rejection.json`。随后每次清除专用副本的路线缓存。
3. 初版候选每次指纹用 LINQ 排序玩家。对官方 DLL 的首轮比较原版中位数 19.75885ms、候选 27.32765ms（+38.3%），记录保留在 `pr-sentinel-official-baseline-initial-verification.json`。之后去掉重复排序，并构建同条件源码原版；新结果仍未达到耗时判据，不宣称前次增加已被消除。
4. 中间构建使用了集合不支持的 `Length` 属性，编译失败；修正为 `Count` 后编译 0 警告、0 错误，失败日志保留。缺夹具路径和错误 SDK 相对路径属于测试准备错误，没有计作游戏通过或回归复现。

## 复现入口与证据边界

先按兼容仓库 `versions.lock.json` 准备私有隔离宿主，确保仅专用 PR 副本关闭适配器同项修复；准备相同提交、相同编译参数的源码基线与候选。两个程序集的 SHA-256 必须与 `pr0481-same-build-inputs.json` 一致。每个对照组由 `tools/run_pr_sentinel_group.py` 运行独立、最多 3 个请求的进程，单项结果上限 75 秒、空闲确认上限 35 秒、单进程上限 1,200 秒；错误即停止该组，保留证据并回收自有进程。最终使用 `python3 tools/verify_pr_sentinel.py` 严格回读。

此场搜索较小，4 个样本不是 4 种独立战斗；不能推广到全部卡组、帧率或 Windows。无头宿主在完成结果和 ready 后的 teardown 退出码 -6 单独记录，不能宣称正常 Steam 退出。原 0.47.3 兼容层的 8 项四卡检查和 32 项扩展检查是历史支持材料，不能当作当前源码候选全套验收。本节记录0.48.1历史采集时的状态；随后已按用户批准提交Draft PR #224，新的0.50.0原生验收与性能门槛仍未完成。

本轮没有记录整机 CPU 负载，也没有证明其他应用空闲；日常游戏当时仍打开，用户另有正常游玩。因此暂停主矩阵仅排除了另一套测试进程的并发，不能证明机器处于受控空闲环境。这组小样本既不能建立无性能增加，也不能独立证明代码造成了性能退化；后续测量需要记录后台负载并使用更大的固定搜索工作量。
